# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase's only new UI surface is the `/login` page and the write-gate redirect that leads to it (D-04/D-05). The feed (`/`), permalink (`/c/{id}`), and camera-capture UI are **unchanged** — all tokens below are inherited from `01-UI-SPEC.md` (approved) and restated here for completeness rather than redefined. Per `02-CONTEXT.md`'s Specifics section: "No app-specific UX styling requirements were expressed beyond the gate mechanics... Standard Google OAuth consent flow is acceptable." Design decisions below fill that gap with sensible, documented defaults — flag any at `/gsd-ui-review` if they don't match intent.

**shadcn state:** Already initialized project-wide in Phase 1 (`components.json` present, `style=new-york`, `baseColor=neutral`, `cssVariables=true`). No re-init needed. This phase reuses the existing `Button` component (`src/components/ui/button.tsx`) — no new shadcn blocks are required.

## Color

**Inherited unchanged from `01-UI-SPEC.md`** — this phase adds zero new color tokens.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` (neutral-50) | `/login` page background |
| Secondary (30%) | `#F4F4F5` (neutral-100) | Not used on `/login` (single-surface page, no card/nav chrome needed) |
| Accent (10%) | `#F59E0B` (amber-500, "civic amber") | See reserved-for list below — **the "Sign in with Google" button is explicitly excluded**, see rationale |
| Destructive/Error | `#EF4444` (red-500) | OAuth callback failure inline error copy (same token/pattern as Phase 1's feed-load-error / submit-error banners) |

**Accent reserved for (unchanged list from Phase 1 — no additions this phase):**
- Primary CTA button ("Report a Problem")
- Camera shutter/capture button
- Selected/active category chip (fill + border)
- Submit button (final publish action)
- Active/focused state of the search-by-ID input (focus ring only)

**"Sign in with Google" button is deliberately NOT amber-accented.** Use Google's standard branded button treatment instead: white background, 1px neutral-300 border, Google's official multi-color "G" logomark, black/neutral-900 text reading "Sign in with Google." This is the documented default per Google's Identity Services branding guidance (recognizable, trust-signaling for an OAuth consent action) and keeps the app's amber accent unambiguous as "this is the report-submission flow" — reusing it here would blur that signal on the one page that has nothing to do with reporting yet.

## Visual Hierarchy

| Page | Primary focal point | Secondary | Tertiary |
|------|---------------------|-----------|----------|
| `/login` | "Sign in with Google" button (Google-branded, 44px min height, centered, ~32px below the heading) | Heading "Sign in to report a problem" | Subtext (why sign-in is needed) above the button; "Continue browsing without signing in" text link below the button; inline error copy (only when `?error=` is present) directly above the button |

`/capture` (anonymous visitor): no visual surface at all — the Server Component gate (D-04/D-05, Pattern 3 in `02-RESEARCH.md`) issues a `redirect()` before any client paint, so there is nothing to render or style for the anonymous-hit case. This is the entire point of the pattern: zero flash-of-gated-content.

`/capture` (authenticated visitor): unchanged from Phase 1 — renders `CaptureClient` exactly as before, no visual change.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Page heading (`/login`) | "Sign in to report a problem" |
| Subtext (`/login`) | "Browsing nearby reports is always open. Signing in with Google is only needed to submit a new report." |
| Primary CTA (this phase's write-gate action) | "Sign in with Google" (button label, Google-branded button per Color contract) |
| Sign-in loading state | "Redirecting to Google…" (button disabled, spinner replaces the Google "G" logo, prevents double-invoking `authClient.signIn.social`) |
| Escape hatch (secondary link, below the button) | "Continue browsing without signing in" → links back to `/` |
| OAuth callback error | "Something went wrong signing you in. Please try again." (rendered inline above the button on `/login`; the button itself stays visible and clickable — no dead end) |
| Destructive confirmation | Not applicable this phase — no sign-out or account-deletion UI ships in Phase 2 (out of scope per `02-CONTEXT.md` Specifics; the only write action gated is complaint submission) |

## UI Considerations

Applicable state considerations resolved: 2 covered, 0 backstop, 0 unresolved (6 dismissed — see reasons)

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | Auth gate + Google sign-in flow (nav) | ✅ covered | Clicking "Sign in with Google" immediately disables the button and swaps to the "Redirecting to Google…" spinner state before the browser navigates away, preventing a double-invoke race on a slow network |
| error | Auth gate + Google sign-in flow (nav) | ✅ covered | A failed OAuth callback (consent denied, provider error, network failure) routes back to `/login` (never a raw 500/blank page) with the inline error copy from the Copywriting Contract; the sign-in button remains visible and clickable to retry immediately |
| overflow | `/login` page content (static-content) | ⚪ dismissed | Single short heading + one line of subtext + one button + one link — fixed, pre-written copy, no risk of overflow at any supported mobile width |
| long-text | `/login` page content (static-content) | ⚪ dismissed | Fixed pre-written copy only (no user-generated or variable-length text exists on this page) |
| empty | n/a this phase | ⚪ dismissed | No list-collection/form/media element is introduced this phase — the feed (the only such element in the app) is untouched (AUTH-04) |
| populated | n/a this phase | ⚪ dismissed | Same reason — no new list-collection/media element |
| partial | n/a this phase | ⚪ dismissed | The sign-in action is a single atomic button, not a multi-field form — no partial-completion state is possible |
| zero-one-many | n/a this phase | ⚪ dismissed | No collection UI is introduced this phase |

**Resolved edge (not a taxonomy row, noted for the executor):** an already-authenticated visitor who manually navigates to `/login` sees the same page render again (no auto-redirect-away logic this phase) — per `02-RESEARCH.md` Open Question 1's stated default ("simplest, no extra check"). Re-clicking "Sign in with Google" simply re-authenticates harmlessly.
