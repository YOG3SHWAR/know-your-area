<objective>
Stand up the Better Auth foundation this whole phase builds on: install the library (after a mandatory package-legitimacy gate), create the single `betterAuth()` server config wired to the project's existing Drizzle/postgres-js `db`, mount its catch-all Route Handler, generate + push its `user`/`session`/`account`/`verification` tables into the live Postgres database, and prove end-to-end that the adapter round-trips against Postgres.

This is the unavoidable prerequisite slice for AUTH-01 — no user-facing write-gate slice (Plan 02) can be wired until the auth core exists and its tables are pushed. Per D-01, Google is the ONLY provider: no Credentials provider, no phone-number schema field, no SMS vendor — not even an unwired placeholder.

RESEARCH.md deviates from `.claude/CLAUDE.md`'s literal Auth.js v5 recommendation (Auth.js entered maintenance mode Sept 2025; its own maintainers now redirect newcomers to Better Auth). Using `better-auth` per RESEARCH.md — CLAUDE.md's own Auth entry invited this re-verification.

Purpose: Give Plans 02/03 a working `auth.ts` + pushed session schema to gate against.
Output: `better-auth` installed, `src/lib/auth.ts`, `src/lib/auth-client.ts`, `/api/auth/[...all]/route.ts`, four auth tables in Postgres, and a passing adapter smoke test.
</objective>

<assumption_delta_decision>
**Primary noun (now generalized):** the write-path identity — Phase 1's per-browser `kya_device_id` becomes a real authenticated `user_id` (Better Auth `user.id`, keyed by the Google account `sub`).

**Decision: promote.** The real `user.id` is promoted to the single primary write-path identity; the `kya_device_id` device identity is demoted to nothing and its module is deleted (Plan 03). This is a clean promote, not add-alongside: per D-03 there is no real user data to reconcile (the user clears existing complaints around this phase), so no device-id → user_id claiming/migration is built. No accepted debt — the old representation is removed, not kept alive alongside the new one.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry → build | Third-party package code (better-auth) enters the app's trust boundary at install time |
| browser → /api/auth/* | Unauthenticated HTTP requests reach the Better Auth catch-all handler |
| app → Postgres | Session/user/account reads and writes cross into the database |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-SC | Tampering | `npm install better-auth` / `@better-auth/cli` | high | mitigate | Blocking-human legitimacy checkpoint (Task 1) before install — [SUS]/too-new packages are never auto-approvable; verify publisher/repo/downloads on npmjs.com |
| T-02-01 | Spoofing | Session cookie signing (`BETTER_AUTH_SECRET`) | high | mitigate | `BETTER_AUTH_SECRET` generated via `openssl rand -base64 32` (CSPRNG, 32+ bytes, ASVS V6) — never a predictable value; HMAC-signed session tokens are Better Auth's default |
| T-02-07 | Information Disclosure | Google client secret | high | mitigate | `GOOGLE_CLIENT_SECRET` read server-side only via `requireEnv` in `src/lib/auth.ts` (a server module) — never imported into a client component or the browser bundle |
| T-02-08 | Tampering | Drizzle adapter SQL dialect (A1) | medium | mitigate | A1 confirmed by the auth-adapter smoke test (Task 3) — a wrong dialect surfaces as a 500, failing the gate before later plans build on it |
</threat_model>
