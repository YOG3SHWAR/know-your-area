<objective>
Ship the phase's user-facing tracer: the write-gate vertical slice. Convert `/capture` into an async Server Component that checks the Better Auth session and redirects anonymous visitors to `/login` BEFORE any client paint or camera/GPS prompt (D-04/D-05), move the existing capture UI verbatim into `CaptureClient.tsx`, and build the `/login` page with the Google sign-in button per the UI-SPEC.

This is the tracer because it wires ONE path through every layer the phase touches — Server Component gate → auth.ts session read → redirect → /login → auth-client → (back to) authenticated render — with a real, runnable e2e verify (the anonymous-redirect path needs no Google credentials and no session fixture). The riskiest architectural bet in this phase is exactly this: does a Server Component `getSession` check structurally guarantee "redirect before any camera/GPS prompt"? Proving that first, on one thin path, catches an architectural dead-end after one commit instead of after the whole phase.

Purpose: Prove the gate architecture end-to-end and deliver the login UI (AUTH-01) + session persistence (AUTH-03).
Output: Gated `/capture`, `CaptureClient.tsx`, `/login` page, session-seeding e2e fixture, and auth-gate e2e coverage.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → /capture | Untrusted request attempts to reach the gated camera/GPS surface |
| browser → /login → Google | OAuth redirect round-trip carrying a `callbackUrl` param |
| Google → /api/auth/callback/google | OAuth callback returns to the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Spoofing | /capture Server Component gate | high | mitigate | `auth.api.getSession()` does a real DB-backed session validation (Pattern 3) — never a cookie-presence-only check; an unauthenticated visitor is redirect()'d before CaptureClient mounts |
| T-02-02 | Tampering | OAuth callback CSRF / state param | high | mitigate | Better Auth performs OAuth state-param + PKCE verification internally on the callback (Don't-Hand-Roll) — no custom CSRF token needed for the auth flow |
| T-02-04 | Tampering | open redirect via `callbackUrl` | medium | mitigate | `callbackUrl` here only ever originates from this app's own gate redirect (hardcoded `/capture`), never arbitrary user input; Better Auth validates `callbackURL` against configured trusted origins (RESEARCH.md Security Domain) |
| T-02-09 | Information Disclosure | flash of gated content | low | accept | The Server Component redirect fires before any client paint (D-05) — there is structurally no gated-content flash to leak; nothing further to mitigate |
</threat_model>
