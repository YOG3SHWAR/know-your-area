## Phase Goal (user story)

**As a** resident who does not trust official civic-reporting channels, **I want to** capture a live geo-tagged photo of a local problem, tag its category, and publish it, **so that** anyone nearby can see photo-verified local issues in a proximity feed and open any report by its ID or permalink.

<objective>
The walking-skeleton tracer: wire ONE happy path through every architectural layer — live camera → live GPS → direct-to-R2 presigned upload → Server Action insert of a PostGIS geometry row with an opaque id → SSR proximity feed that renders it — and prove it with a documented local full-stack run and an E2E test.

Purpose: Prove the risky architecture (direct-to-R2 upload past Vercel's 4.5MB limit, Drizzle geometry/geography distance query, App Router Server Action write) end-to-end on one committed path before any expansion. Plans 03 and 04 refine the capture and feed slices this tracer establishes.
Output: A running app where publishing a complaint makes it appear on the nearby feed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/upload-url | Untrusted client requests a presigned URL; key/content-type must be server-controlled |
| browser → R2 (direct PUT) | The photo bytes bypass the app server entirely; only the signed constraints protect the object |
| browser → submit Server Action | Untrusted `{category, lat, lng, accuracy, photoKey}` crosses into the DB |
| browser → device-id cookie | The cookie is the de-facto identity token this phase relies on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-02 | Tampering | /api/upload-url presigned PUT | high | mitigate | ContentType pinned in the signed `PutObjectCommand` and restricted server-side to image/jpeg|webp (RESEARCH Pitfall 6); R2 rejects a mismatched upload. |
| T-01-03 | Tampering | R2 object key | high | mitigate | Key is generated server-side as `complaints/${publicId}.${ext}`; a client-supplied key/path is never used (prevents key injection / path traversal). |
| T-01-07 | Tampering | submitComplaint payload | high | mitigate | `submissionSchema.parse` re-validates category enum + India coord bounds + accuracy before insert. |
| T-01-08 | Spoofing | device-id cookie | medium | mitigate | Value from `crypto.randomUUID()` (CSPRNG), httpOnly + SameSite=Lax. |
| T-01-04 | Spoofing | GPS coordinate source | medium | mitigate | Location read live from `navigator.geolocation` at submit; EXIF is never read (canvas re-encoding strips it and it is spoofable). Residual GPS spoofing beyond the bounds check is accepted for Phase 1 — real anti-spoof (VERIFY-02) is Phase 4. |
| T-01-DoS | Denial of Service | submit via resettable stub identity | low | accept | Explicit Phase-1 scope gap — rate limiting is Phase 4 (VERIFY-04); zod validation still blocks malformed payloads. |
</threat_model>
