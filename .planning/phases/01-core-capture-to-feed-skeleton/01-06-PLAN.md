<objective>
Close **G-01-EXTRA-1 (blocker)** at the code level: in production, `GET /api/feed` returns HTTP 500 on every request (confirmed via curl against the Vercel deploy), so the home feed unconditionally shows the "Couldn't load reports…" banner even though it works on localhost. The root cause is inconclusive without Vercel function logs / env-dashboard access (unavailable to the investigating agent), but `src/lib/db/client.ts` instantiates `postgres(requireEnv("DATABASE_URL"))` with **zero** connection options, which is the common root of the top-ranked hypotheses (missing TLS against Supabase; prepared statements incompatible with a transaction-mode pooler). This plan applies the defensive code fixes that are correct regardless of which hypothesis is confirmed, and makes the real error visible in logs.

Purpose: make the postgres.js client compatible with Supabase's hosted-connection requirements, and stop swallowing the real exception so the remaining env-level diagnosis (handled by the human-verify checkpoint in plan 01-07) can be completed against actual log output.
Output: hardened DB client with a unit-tested options builder, and a feed route that surfaces the failure server-side.

**Note — this plan cannot fully close G-01-EXTRA-1 by itself.** The remaining root cause is a production env/config question (does `DATABASE_URL` point at Supabase's IPv4-reachable Session/Transaction pooler, is it scoped to Vercel Production, is the Supabase project un-paused) that no code change can decide. That verification is plan **01-07** (blocking human-verify), which depends on this plan's fix being deployed.
</objective>
