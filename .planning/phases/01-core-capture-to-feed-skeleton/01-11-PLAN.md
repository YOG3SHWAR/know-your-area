<objective>
Close **G-01-2** (blocker): on production (https://knowyourarea.in), on a real device, capturing a photo shows "Load failed" and the Publish Report button never enables — the capture→upload→publish flow is blocked, while the identical code works on localhost.

Root cause is already fully diagnosed (do not re-investigate — see `.planning/debug/production-capture-load-failed.md`): the Cloudflare R2 bucket's CORS AllowedOrigins was configured only for `http://localhost:3000` during Plan 01-02; the production origin was never added. The browser→R2 presigned PUT is a real cross-origin request subject to that CORS policy, so it is blocked in production. Safari surfaces the blocked fetch as `TypeError: Load failed`, and `CameraCapture.tsx`'s upload catch block reflects `err.message` verbatim to the UI and returns before calling `onCaptured(key)` — so `photoKey` in `page.tsx` stays null and `disabled={!photoKey || ...}` keeps Publish disabled forever.

Two-part fix, each addressing one arm of the cause:
1. **Infra (human-only, no repo change):** add the production origin to the R2 bucket CORS policy. The coding agent has no R2 credentials, so this is declared as `user_setup` and its live effect is confirmed as an end-of-phase human-check (the only check that can prove the production unblock).
2. **Code:** stop leaking raw `err.message` from the upload catch block; render a sanitized, actionable message consistent with the existing camera/geolocation error handling in the same file. Also update README's CORS docs so a future contributor deploying fresh does not re-hit this gap.

Purpose: unblock the core capture-to-publish loop on real production devices and stop leaking raw browser network internals into the UI.
Output: a sanitized upload-error path with e2e coverage, README CORS docs that include the production origin, and a documented human infra step + live production confirmation.
</objective>
