<objective>
Close **G-01-9 (major, UAT test 9)**: after a user captures a photo on `/capture`, the live camera keeps playing and nothing signals that a photo was taken. The blocked-on symptom (per 01-UAT.md): "after capturing the photo, there is still live camera and no feedback or photo which was captured is being shown." This also made the double-tap-Publish guard (already present in `src/app/capture/page.tsx` via the `publishPhase !== "idle"` single-flight guard) impossible to reach and verify.

Root cause (per `.planning/debug/capture-preview-not-shown-after-photo.md`): `CameraCapture.tsx`'s render has exactly one status-conditional branch (`status === "starting"`); the `<video>` playing the live `getUserMedia` MediaStream is rendered unconditionally and its tracks are only stopped on unmount, never after a capture. The captured frame is drawn to an off-screen `<canvas>` used purely to produce the upload Blob, then discarded — it never reaches the DOM. The Capture button's label/disabled logic also does not distinguish `captured` from `ready`, so it reverts to "Capture Photo". This is both an implementation gap and an upstream design-contract gap: 01-UI-SPEC.md's Capture-screen state table never defined a post-capture confirmation state.

Fix (the three `missing` items from the gap):
1. Surface the captured frame as a static preview and stop the live stream on success, so the user sees clear confirmation before the category/Publish step. The preview is rendered as an `<img>` (the same canvas that already carries the D-02 burned-in geotag/timestamp overlay), so the user also sees the tamper-evident overlay on their own photo.
2. Give the capture control a distinct captured state ("Photo captured — Retake?") that itself signals success, with a working Retake that restarts the camera and clears the pending photo.
3. Add the missing 01-UI-SPEC.md "populated"/post-capture-confirmation state-table row.

Purpose: make the core live-capture loop (D-01) legible so a user knows their photo was taken, and so the SUBM-01 capture→publish flow is actually usable end-to-end on a real device.
Output: a revised `CameraCapture.tsx`, a new e2e test reproducing the missing-feedback failure, and the closed UI-SPEC state-table gap.

**Scope note.** This is a UX-completeness fix on the D-01 live-capture flow, not a REQUIREMENTS.md failure — all Phase 1 requirement IDs (SUBM-01/02/03/06, FEED-01/03/04) remain satisfied by Plans 01-01…01-09. `requirements: [SUBM-01]` is cited because SUBM-01 governs the live-in-app-camera capture flow this preview completes. Explicitly OUT OF SCOPE: `G-01-EXTRA-2` (home-page SSR webpack error — diagnosed as a transient dev-server cache artifact with no code fix, excluded by the developer; re-verified manually via a dev-server restart), and the already-resolved gaps G-01-3, G-01-4, G-01-EXTRA-1.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device browser (canvas capture) → client render | The captured frame is drawn to a canvas and shown back to the same user as a preview; it does not cross a network boundary differently than before. |
| device browser (canvas render) → stored image bytes (R2) | Unchanged — the upload Blob is still produced from the same canvas after the D-02 overlay burn-in; this plan only ADDS a read-back (`toDataURL`) for display and does not alter what bytes are uploaded. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-11 | Tampering / Repudiation | captured-photo preview vs. uploaded bytes | low | accept | The `<img>` preview is a read-back of the SAME canvas whose Blob is uploaded, so it cannot show the user one image while uploading another. | T-01-12 | Information Disclosure | preview `<img>` data URL | low | accept | The data URL is generated in-page from the user's own capture and rendered as an `<img src>` (no markup interpretation, no injection surface); it is never persisted or sent anywhere new. |
| T-01-SC | Tampering | package installs | n/a | accept | This plan installs no npm/pip/cargo packages (edits `CameraCapture.tsx`, `capture.spec.ts`, and a planning doc only) — no supply-chain surface is introduced, so no `[ASSUMED]`/`[SUS]` legitimacy checkpoint is required. |
